# Рефлексия

## Почему эта задача

Я выбрал RepoTruth Agent, потому что это очень практичная задача на стыке ИИ, разработки и честной оценки проектов. В резюме, на хакатонах и в учебных отборах люди часто пишут короткие утверждения: “сделал RAG”, “есть FastAPI backend”, “проект запускается в Docker”, “есть тесты”. Но по одному README невозможно понять, действительно ли это реализовано. README может устареть, быть слишком оптимистичным или просто описывать планы, а не готовый код.

Мне понравилась идея сделать агента, который не просто отвечает красивым текстом, а ищет проверяемые доказательства. Поэтому RepoTruth устроен как evidence-based workflow: LLM сначала помогает понять, что именно нужно проверить, затем выбирает tools для каждого claim, Python-инструменты собирают реальные следы в репозитории и GitHub API, а LLM-verifier выносит verdict только по evidence. Для HR, техскринеров, жюри и самих кандидатов это полезнее, чем обычный обзор GitHub-проекта.

Особенно важная часть проекта — evidence contract. Если агент пишет `confirmed`, он обязан показать путь, номер строки и фрагмент кода. Это снижает риск галлюцинаций и делает результат воспроизводимым. Для меня это главный инженерный урок проекта: LLM должна не заменять проверку, а управлять проверяемыми инструментами.

## Где агент ломался

Первый failure case — слишком общие claims. Например, утверждение “проект хорошо спроектирован” почти невозможно честно подтвердить простым поиском по файлам. Для таких claims агент может найти косвенные признаки, но не должен писать `confirmed`. В MVP такие claims лучше получают `partial` или `missing`.

Второй failure case — сложные claims про архитектуру или AI-функции. По нескольким совпавшим словам в репозитории нельзя честно подтверждать полноценную реализацию. Поэтому verifier получает только найденные evidence и должен явно отличать прямое доказательство от похожей, но нерелевантной строки.

Третий failure case — непредсказуемость LLM JSON. Даже сильная модель иногда возвращает пояснения вокруг JSON или выбирает слишком общие поисковые слова. Поэтому в проекте есть JSON extractor, Pydantic-валидация и allow-list tools. Я специально убрал offline fallback: если LLM-router не работает, агент честно падает, потому что для этой задачи важно показать именно агентное поведение, а не скрытый grep-скрипт.

## Что сделал бы дальше

Если бы было больше времени, я бы добавил baseline comparison: обычная LLM получает только README и claims, а RepoTruth получает tools и evidence. Это наглядно показало бы, где простая LLM верит описанию, а агент находит реальное состояние кода.

Еще я бы добавил веб-интерфейс для HR и кандидатов, поддержку private repositories через GitHub App, больше языков программирования и semantic code search. Сейчас поиск в основном основан на зависимостях, путях и строковых паттернах. Для MVP этого достаточно, но для production-версии полезен AST-анализ и отдельные проверяющие правила для Python, JavaScript, Go и Java.

Также я бы расширил режим для кандидатов: агент мог бы не только говорить `confirmed/partial/missing`, но и предлагать честную формулировку для резюме. Например, вместо “реализовал полноценный RAG” предложить “добавил embeddings и Chroma; retrieval pipeline требует доработки”. Это делает инструмент не карательным, а обучающим.
